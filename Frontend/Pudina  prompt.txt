# PART 1 — PRODUCT REQUIREMENTS DOCUMENT (PRD)

## 1. Product Overview

TrafficVision AI is an intelligent traffic management and route optimization platform designed to help commuters, administrators and emergency services understand road conditions, identify traffic incidents, predict congestion and select optimized routes.

The platform combines:

- Interactive map-based navigation.
- Live traffic information from available traffic providers.
- AI-based traffic congestion prediction.
- Community-driven incident reporting.
- Intelligent incident verification and network-impact analysis.
- Adaptive traffic signal simulation.
- Emergency vehicle priority routing.
- Multi-factor route optimization.
- Authorized road-camera monitoring.
- Laptop webcam demonstration mode.
- AI-powered image and video analysis through a configurable NVIDIA API integration.
- Telegram bot integration for camera access, alerts, images, videos and AI analysis.

The platform must function as a coherent working application, not a collection of disconnected UI screens.

## 2. Primary Objectives

1. Help users compare available routes between two locations.
2. Calculate shortest and fastest routes.
3. Display distance, ETA, congestion and incident information.
4. Predict congestion 15–30 minutes ahead.
5. Detect duplicate and potentially false incident reports.
6. Analyze how road incidents affect connected road segments.
7. Simulate optimized traffic signal timings.
8. Calculate priority routes for emergency vehicles.
9. Allow users to inspect authorized traffic cameras.
10. Allow users to capture images and videos using their laptop camera.
11. Deliver camera media and AI analysis through the website and Telegram.
12. Provide administrators with tools to monitor and manage the traffic network.

## 3. Target Users and Roles

### A. General User / Commuter

- Search for locations.
- Select source and destination.
- Compare available routes.
- View traffic conditions.
- Report incidents.
- Inspect available cameras.
- Request snapshots and camera clips.
- Receive traffic alerts.
- Connect a Telegram account.

### B. Administrator

- Monitor traffic conditions.
- Review incident reports.
- Approve, reject or merge reports.
- Manage camera registrations.
- Inspect traffic predictions.
- Monitor AI analysis jobs.
- Review road closures and diversions.
- Access traffic analytics.

### C. Emergency Services / Emergency Demonstration Role

- Select emergency vehicle type.
- Enter an emergency destination.
- Calculate priority routes.
- View predicted congestion.
- Simulate priority passage through traffic signals.
- Compare emergency and normal route ETAs.
- View estimated time saved.

This is a simulation and decision-support feature, not a real emergency dispatch or traffic-control system.

# 4. FUNCTIONAL REQUIREMENTS

## MODULE 1 — Interactive Traffic Map

### Required features

- Interactive, responsive map.
- Map zooming, panning and location selection.
- Source and destination markers.
- Search for places and addresses.
- Display road networks and junctions.
- Display route polylines.
- Display incident markers.
- Display available camera markers.
- Display traffic congestion overlays.
- Display predicted congestion overlays.
- Show selected road or junction details.

### Map technology

- OpenStreetMap for base geographic data.
- MapLibre GL JS for map rendering.
- Suitable tile provider or properly configured self-hosted tiles.
- Geocoding provider behind a configurable service interface.

Do not treat OpenStreetMap as a live traffic data provider.

### Traffic layer legend

Use consistent visual meanings:

- Green: flowing traffic.
- Yellow: moderate traffic.
- Orange: heavy traffic.
- Red: severe congestion.
- Grey: unavailable or unverified traffic information.
- Blue: selected route.
- Purple: predicted congestion.
- Red incident marker: reported or verified incident, with its verification status clearly indicated.

Provide a legend that explains every map layer.

### Data provenance

Every traffic layer must identify its source:

- External live traffic API.
- Authorized camera observation.
- User-reported incident.
- Historical data.
- Simulated data.
- AI-generated prediction.

Never display simulated information as verified live traffic.

## MODULE 2 — Traffic Data Integration

### Preferred data architecture

**Base map:** OpenStreetMap  
**Map renderer:** MapLibre GL JS  
**Live traffic provider:** TomTom Traffic API, subject to available free quota and account terms  
**Alternative providers:** Configurable provider adapter  
**Routing network:** OpenStreetMap road graph  
**Routing engine:** Dijkstra / A* or OSRM where appropriate

### Required traffic information

Where supported by the selected provider:

- Current road speed.
- Free-flow road speed.
- Congestion level.
- Traffic incidents.
- Road closures.
- Road restrictions.
- Incident locations.
- Incident timestamps.
- Traffic flow measurements.

### Integration rules

1. Keep external API keys on the backend.
2. Never expose secret API keys in browser code.
3. Cache traffic responses according to provider terms.
4. Handle API timeouts and quota exhaustion.
5. Show the last successful update timestamp.
6. Show a clear unavailable state if the provider fails.
7. Do not fabricate traffic measurements when an API returns no data.
8. Keep the provider replaceable without rewriting the frontend.

If no live traffic provider is configured, demonstrate the map with clearly labelled simulated traffic data.

## MODULE 3 — Route Search and Optimization

### User inputs

- Source location.
- Destination location.
- Optional route preferences.
- Optional vehicle type.
- Optional route avoidance preferences.

### Route options

The platform must calculate and compare:

1. Shortest route.
2. Fastest route.
3. Lowest-congestion route.
4. Most reliable route.
5. Recommended balanced route.

### Required route information

For each option:

- Total distance.
- Estimated travel time.
- Current congestion.
- Number of reported incidents.
- Road closure warnings.
- Estimated fuel consumption.
- Route reliability score.
- Important route segments.
- Last traffic data update.

### Multi-factor route scoring

Implement a configurable weighted scoring system.

Possible factors:

- Distance.
- Estimated travel time.
- Congestion.
- Road closures.
- Incident severity.
- Estimated fuel consumption.
- Route reliability.

Normalize the factors before combining them. Do not add kilometres, minutes and percentages directly.

The system should support configurable weights and a user preference interface.

Example:

- Time-sensitive journey: higher ETA weight.
- Fuel-efficient journey: higher fuel-consumption weight.
- Reliability-focused journey: higher reliability weight.

Explain why the recommended route was selected.

Display alternative routes rather than silently selecting one.

### Routing algorithms

Use Dijkstra or A* for graph-based routing.

The road graph should represent:

- Road nodes.
- Road segments.
- Segment lengths.
- Direction restrictions.
- Road connectivity.
- Road closure status.
- Traffic-dependent edge costs.

For dynamic routing, update edge weights when new traffic or incident data becomes available.

OSRM may be used as an additional routing service, but do not assume it automatically accounts for live traffic.

## MODULE 5 — AI Congestion Prediction (MANDATORY)

### Objective

Predict congestion 15–30 minutes ahead using available traffic and contextual information.

### Input features

- Historical traffic measurements.
- Current traffic speed.
- Road capacity.
- Time of day.
- Day of week.
- Traffic incidents.
- Weather information, when available.
- Nearby road congestion.
- Historical patterns.

### Prediction outputs

- Predicted congestion level.
- Predicted speed or speed category.
- Prediction horizon.
- Confidence or uncertainty estimate.
- Affected road segments.
- Recommended alternative routes.

### Model implementation

Use a practical, explainable baseline before introducing a complex model.

Possible approaches:

- Gradient boosting.
- Random Forest.
- Time-series forecasting.
- Regression models.
- Historical pattern baselines.

The exact algorithm should be selected based on the available dataset.

### Important requirements

- Support 15-minute and 30-minute prediction horizons.
- Display actual versus predicted traffic where ground truth is available.
- Record prediction timestamps.
- Track prediction errors.
- Display confidence or uncertainty.
- Identify whether the prediction is trained, baseline-generated or simulated.
- Never claim high prediction accuracy without evaluation.

If real historical data is unavailable, create a labelled synthetic dataset and document the assumptions.

## MODULE 6 — Intelligent Incident Detection and Network Impact Analysis (MANDATORY)

### Duplicate incident detection

Identify potentially duplicate reports using:

- Geographic proximity.
- Incident category.
- Submission time.
- Text similarity.
- Similar media, when appropriate.

Present duplicate candidates for verification.

Do not merge reports solely because they are close together.

### Incident severity estimation

Consider:

- Incident type.
- Number of affected lanes, if known.
- Road capacity.
- Reported severity.
- Traffic conditions.
- Available camera observations.
- Potential obstruction duration.

Output:

- Severity category.
- Confidence.
- Evidence.
- Verification status.

### Graph-based network impact analysis

When an incident is confirmed or simulated:

1. Identify the affected road segment.
2. Identify connected segments.
3. Calculate affected routes.
4. Estimate detour impact.
5. Identify alternative paths.
6. Show potentially affected junctions.
7. Simulate road closure or lane blockage.
8. Recommend diversions.

Display the affected road network visually.

Distinguish a simulated road closure from an actual reported closure.

## MODULE 11 — NVIDIA AI IMAGE AND VIDEO ANALYSIS

### Objective

Analyze camera snapshots and recorded clips using a model accessed through NVIDIA's API catalog.

### Provider

NVIDIA API Catalog / NVIDIA NIM.

The exact model will be chosen later.

Do not hardcode a specific model name or endpoint.

### Architecture requirement

Create a provider-independent AI service layer.

Suggested interface:

- `analyzeImage()`
- `analyzeVideoFrames()`
- `getAvailableModelConfiguration()`
- `validateModelCapabilities()`
- `getAnalysisStatus()`

The NVIDIA integration must be replaceable without rewriting the camera, Telegram or dashboard modules.

### Model selection configuration

Store configurable settings:

- Provider.
- API base URL.
- Model identifier.
- API key reference.
- Supported input modalities.
- Request timeout.
- Maximum image size.
- Maximum video duration.
- Frame sampling interval.
- Retry policy.

The actual NVIDIA model and endpoint will be configured after model selection.

### Image analysis

The analysis should attempt to identify:

- Approximate vehicle count.
- Vehicle categories where recognizable.
- Traffic density.
- Queue length or queue severity.
- Visible congestion.
- Road obstructions.
- Possible accidents.
- Possible roadblocks.
- Unusual traffic conditions.
- Confidence or uncertainty.
- Important visual observations.

### Video analysis

Do not assume that an image model can accept an entire video file.

Use a controlled video-processing pipeline:

1. Receive the uploaded video.
2. Validate format, size and duration.
3. Extract representative frames using FFmpeg.
4. Sample frames at a configurable interval.
5. Submit frames to the selected multimodal model.
6. Analyze temporal changes across the sampled frames.
7. Generate a consolidated report.
8. Save the analysis result.
9. Display the result on the website.
10. Send the result to Telegram.

If the selected model explicitly supports direct video input, allow a configurable direct-video adapter.

### Structured AI output

Require a consistent JSON response structure similar to:

{
  "media_id": "unique-id",
  "analysis_type": "image_or_video",
  "source": "demo_camera_or_authorized_camera",
  "capture_timestamp": "ISO-8601",
  "processing_timestamp": "ISO-8601",
  "region": "selected-region",
  "traffic_density": "low_moderate_high",
  "estimated_vehicle_count": null,
  "visible_obstructions": [],
  "possible_incidents": [],
  "observations": [],
  "confidence": null,
  "limitations": [],
  "summary": "Human-readable summary"
}

Validate model output before saving it.

If the model returns invalid JSON, attempt controlled parsing or return a clear processing error. Never silently fabricate missing fields.

### Critical AI limitations

- AI image analysis is not proof that an accident occurred.
- A single image cannot establish vehicle speed.
- A video sampled at intervals cannot guarantee continuous tracking.
- Vehicle counts are estimates and should be labelled accordingly.
- The system must not identify people.
- Do not store unnecessary identifiable faces or number plates.
- The AI must communicate uncertainty.

### Result distribution

Every successful analysis must be available through:

1. Website dashboard.
2. Media details page.
3. Telegram bot.

The website and Telegram must display the same stored analysis result, not run separate inconsistent analyses.
